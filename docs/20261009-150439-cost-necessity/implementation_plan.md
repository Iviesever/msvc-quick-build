# Static review and acceptance contract

## Design

Use independent product-consumer and acceptance-provenance audits, followed by a
separate decision JSON and matched English/Chinese report. The new report is a
static review, not an executable protocol, mutable grant or replacement for the
21000-byte frozen preparation. Its SHA-256 remains
f3c978a791f5797d62739dde24759003e231eb58892f7eaf689852ef62a0e1ae.

The accepted handoff and standing continuation instruction authorize this
isolated docs branch and normal Connector integration. The using-git-worktrees,
executing-tasks, requesting-code-review and verification-before-completion
workflows apply. No product behavior is changed, so no compiler, project test,
fixed-substitute baseline or new test suite is part of the verification budget.

## Sequential work and review checkpoints

1. Read back main, PR253, frozen Draft PR250 and the latest #198 handoff; confirm
   repository constraints and create the isolated branch from the exact main.
2. Independently trace actual source consumers and examine the historical study
   purpose, frozen seven blockers and authoritative acceptance requirements.
   Record exact commits, paths, blobs, file hashes and line ranges for findings.
3. Decide whether a new real-cost execution has a currently selected product
   decision and pre-data outcome rule. A negative current decision is a complete
   result; it must not assert that future measurement could never be useful.
4. Classify semantic/shape bounds, measurement representation, observer resource
   ceilings, historical consumption and the separately scoped external-no-op
   gate. Keep unknown criteria unknown and preserve all closed preparation fields.
5. Write the bilingual report, machine-readable decision and walkthrough. Name
   one finite next product/acceptance prerequisite, with an explicit absence
   outcome; do not prescribe a new experiment to complete paperwork.
6. Obtain fresh independent final review. Resolve material source, scope,
   language or authorization findings before submission. Static checks must
   confirm existing 711 tracked blob/mode pairs, frozen bytes, exact new-file
   scope, referenced source identities and bilingual structure.
7. Submit the verified files through Connector Git Data APIs, read back exact
   blobs/tree/parent/PR file coverage, retain an exact-head COMMENT review and
   inspect actual applicable workflow/job/step/log evidence. Mark ready and
   merge normally only when applicable checks and review are sufficient.
8. Verify actual merge parents/tree/main and applicable main CI, update the
   authoritative #198 handoff, and package the immutable review and delivery
   evidence with per-entry hashes and an independent archive readback.

## Invariants and limits

The original preparation remains PREPARATION_ONLY_BLOCKED with 15 strict integer
zero real budgets, 10 null future choices, seven blockers and four false
authorities. Review completion cannot change product-cost HOLD, PR250
integration HOLD or real-execution BLOCKED. Historical process/API consumption
is retained, never refunded; absent observations stay absent.

The report must not conflate the historical Linux/GCC model/API windows with
Windows/MSVC, default-path, high-frequency, persistence, total-memory, cleanup
or Rium qualification. Fixed-byte validation does not authenticate a producer.
No old runner, analyzer, project module or workload is executed. Read-only
source audits and administrative Git/CI operations are not performance samples.

All existing tracked files, 51 workflows, product code, tests, VERSION and old
evidence remain unchanged. Evidence files are separate from the repository.
The new bilingual pair is reviewed directly because the unchanged documentation
CI enumerates only its existing document pairs; actual CI coverage is reported
without implying that it verified this new decision or ran native workloads.
