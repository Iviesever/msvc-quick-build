## Changes since v5.5.0

- **Build and foreground execution are separated.** Ordinary and module builds return owned launch data; a separate foreground runner executes it after build-side objects leave scope. Build failure does not launch the program. Existing arguments, working directory, standard streams, sanitizer runtime policy and child exit-code propagation remain. Environment bootstrap now redirects its own input from `nul`, preserving piped input for the foreground program. Scope exit is not proof that external writers have stopped. See [BuildCompletion](../cpp/src/app/targets/BuildCompletion.cpp) and [VisualStudioEnvironment](../cpp/src/msvc/toolchain/VisualStudioEnvironment.cpp).
- **Identical include-root spellings avoid redundant conversion.** [#194](https://github.com/Iviesever/msvc-quick-build/pull/194) uses exact native-path equality before the existing identity fallback. Different spellings still use that fallback. Order, duplicates, cache validation and late freshness checks are retained. This structural optimization is not a promise that every workload is faster.
- **Internal lifecycle groundwork is additive and opt-in.** Process cancellation, scheduler admission/batches, physical write-domain admission and read-only known-write inventories support further engineering. They do not enable CLI cancellation, reusable project transactions, automatic recovery or residency. See [process lifetime](PROCESS_LIFETIME.md) and [write-domain admission](WRITE_DOMAIN_ADMISSION.md). M1b and later v6.0 work remain unfinished.
- **Evidence recording and research scope are corrected.** [#193](https://github.com/Iviesever/msvc-quick-build/pull/193) replaces repeated whole-history writes with an append journal and compatible final JSON. [#195](https://github.com/Iviesever/msvc-quick-build/pull/195) separates unallocated compiler-PDB research from ordinary changes. [#188](https://github.com/Iviesever/msvc-quick-build/pull/188) preserves exact sources, actual measured programs and first failures. These are validation improvements, not additional public CLI features.

## Compatibility, installation and migration

**Existing CLI commands and `mqb.json` files do not require a new migration for this candidate.** The CLI parser, configuration schema and compile/link/archive cache-file implementations are byte-identical to the compared v5.5.0 source. This is a scoped source comparison, not a guarantee for arbitrary external scripts or damaged caches. Existing ordered options, typed MSVC admission, output repair and late freshness checks still apply; no cache purge is required merely to adopt this candidate.

`--run` remains a foreground operation with the existing argument/stream/exit-code contract, outside any future build cancellation policy. `plan` and `compdb` do not adopt the new write-domain reservation API. Default parallelism is not replaced by a forced `-j 1`. C++23 and Windows/MSVC remain the product scope; no new platform or toolset certification is implied.

The public compiler-option boundary is unchanged: MQB uses `/Z7`, rejects `/Zi` and `/ZI`, reserves `/Fd`, and removes ambient `CL` / `_CL_` from compiler invocations. Final linker PDBs and external objects, libraries, PCH/IFC inputs are not all covered by that boundary. Do not read it as a universal PDB-safety claim or silently change a research fixture's flags. Details and the retained failures are in [PROCESS_LIFETIME.md](PROCESS_LIFETIME.md).

Internal C++ callers must review the changed process, scheduler and admission contracts; unchanged CLI syntax is not a binary-ABI compatibility promise. In particular, the opt-in managed process policy is inappropriate for foreground applications intended to leave descendants alive. A write-domain marker is not permission to reclaim abandoned state.

Developer scripts using `Recorder` must use its context manager or finalize on normal and exceptional exits. Read `calls.jsonl` during execution; `calls.json` is generated at controlled completion. A valid prefix after forced termination is not a complete experiment, and journaling is not a power-loss durability guarantee. See [DEVELOPMENT_EN.md](DEVELOPMENT_EN.md).

The stable package contract remains flat and runtime-only: `mqb.exe`, `VERSION`, `install.bat`, `install.ps1`, `uninstall.bat`, `uninstall.ps1`, `LICENSE`, with a ZIP checksum sidecar. Installation scripts are unchanged. Do not substitute a CI package labelled 5.5.0 for the official v5.5.0 release or advertise it as v5.6.0. Documentation and these limitations stay in the repository/Release description, not in the runtime ZIP. See [installation](INSTALLATION_EN.md) and [self-hosting](SELF_HOSTING_EN.md).

## Explicit residual-risk disposition

This decision permits preparation of the **unchanged-product, one-shot CLI release candidate**. It is not a retrospective pass for a failed experiment, an explanation of its cause, or publication authorization. The original artifact fields `release_authorized=false`, `historical_risks_cleared=false` and historical HOLD entries stay unchanged. Current acceptance is justified by the separately frozen, genuinely changed candidate, its accepted correctness evidence and original current gates—not by retrying an unchanged failed head.

Users requiring predictable cold-build latency should retain their validated version and qualify this candidate on representative projects before adoption. Risk acceptance must be carried into the final Release description; silently dropping these qualifications reopens release review.

## Stop and rollback conditions

**Stop publication** for a new public-path correctness/freshness/diagnostic regression, an exact-version required check failure or unexpected skip, missing source/binary identity, incomplete first evidence, or a new violation of the unchanged applicable performance gate. Do not raise thresholds, drop samples, refill a spent budget, re-run until green, subtract guessed observer cost or classify an unknown failure as research solely to pass.

A product repair or rollback requires evidence identifying the affected change and a focused reviewed commit. Any such change invalidates the old product freeze and requires a new impact-specific validation plan; the already-consumed #188 budget is not reusable. Until a justified change exists, retain the accepted candidate and known risk rather than inventing a repair or silently undoing accepted correctness work.

For a deployment rollback, keep the official v5.5.0 executable/package and project configuration. Stop related builds and establish that their tools have finished before changing generated state. Use a separate project/output copy or a clean rebuild when comparing versions; do not share writable output between concurrent versions. Never delete an unresolved write-domain claim, PDB or IDB as proof of safe recovery. Downgrading an executable does not prove abandoned writers are gone. Historical tags and assets must not be overwritten.

## Remaining release handoff

After this documentation/risk review, proceed directly to an **independent VERSION/release PR**, not another recorder migration or another frozen 584-pair run. Keep unrelated product and research changes out. Read the current main/CI again and prove that product/build/package identities still match the accepted candidate before changing `VERSION` to `5.6.0`.

That exact version must pass Windows Debug and Release, seed/Stage 0/1/clean 2, packaged embedded version, seven-file ZIP/checksum and installer lifecycle, plus independently preregistered ABBA under the unchanged gate. Retain the actual programs and first failures. The current unversioned candidate's results do not substitute for these checks; no new cumulative or research budget is granted here.

Merging the VERSION PR triggers the existing [publication contract](SELF_HOSTING_EN.md): Native Release validates that exact main commit and publishes its already-validated Stage 1 package without rebuilding at publication. Include this document's scope, compatibility and risk qualifications in the generated Release description using the normal publication process; do not assume generated PR titles communicate them. An unauthorized or failed publication gate stays stopped. This documentation change does not create a tag, Release or new binary asset.
