# 目标级编译检查与仅调度未命中项

**[English](TARGET_COMPILE_WAVE.md) | 简体中文**

本轮建立在 [Persistent Warm Fast Path](WARM_FAST_PATH_ZH.md) 描述的调用内文件系统证据之上，将普通 executable/DLL 与静态库的编译检查、执行分开，但不向外暴露可执行陈旧计划的 API。

## 所有权与阶段

`src/orchestration/incremental/TargetCompileWave.hpp` 是两个 target coordinator 共用的 orchestration 私有实现。符合条件的目标先并行调用一次无副作用的 `inspect()`，直接按源文件索引保存命中结果，为未命中项保留本次检查使用的确切 request 和 inspection，再建立紧凑的源文件索引队列。`execute_inspected()` 消费该检查结果，不重新打开 compile cache，不重复规划。

检查结束后，只有未命中项保留完整 request 和 plan；存储量为每个 TU 一个指针槽，加上每个未命中项的请求与计划。检查决定不持久化，也不会作为公共执行凭证返回。公共 `inspect()` 仍然只提供诊断数据；公共 `run()` 仍然先重新检查。私有消费接口仅供 `run()` 和本次调用拥有的 wave 使用。

## 调度约定

检查继续使用既有有界并行策略。执行调度器接收的是未命中项数量，而非目标总 TU 数。全命中时不进入执行调度器；一个未命中项直接在调用线程运行；多个未命中项继续使用既有 worker policy，并以实际未命中数量限制并发。检查失败时，即使较早的 TU 已规划出编译动作，也不得开始执行。执行失败保留调度器的停止行为、按原始源文件索引选择错误的规则，以及禁止 link/archive 的约束。

一至两个 TU 的小目标与已强制失效的目标保留原先的检查并执行路径，避免为这些负载增加第二阶段。固定 `-j1` 的检查循环只激活一次共享证据。执行阶段明确暂停检查证据，包括嵌套调用场景。

**零执行任务不等于零检查线程。** 大目标在固定 `-j4` 且全命中时仍创建三个检查后台线程。本轮不声称消除了这些线程，也不因队列变小就宣称延迟改善。冷构建和部分重编译可能分别创建检查、执行两组 worker；新增调度开销和减少的阶段重叠必须通过实测评估。

## 新鲜度与失败边界

目标的共享依赖复验屏障保留在整个 wave 结束后，包括未命中项执行之后。头文件可能在编译器运行期间改变，因此只在执行前复验并不充分。共享证据窗口被拒绝后，丢弃所有较早结果，并在暂停共享的情况下走原先路径强制重建整个目标。只有成功完成后才能进入链接或归档。

这保留了既有的时间戳竞态模型，并非原子的文件系统快照；不承诺防御任意保留时间戳的变更或屏障之后的变更。source/output snapshot、缓存格式、签名、工具配方、include-search freshness 与 Modules/Header Units 依赖顺序均不变。本轮不引入编译输出证据移交、持久化 cache pack、daemon 或 watcher。

## 验证与性能证据

既有 target coordinator 测试程序新增检查/执行调度摘要、缓存打开次数、紧凑索引到原始源文件索引的映射、原始 warning 保留、静态库 wave 对称性、固定 `-j1`、检查失败阻止执行，以及在唯一未命中的编译器调用内部注入公共头变更的测试。最后一项要求先执行一次编译，再强制编译全部四个 TU，最后只链接一次。原有并发失败、重复产物、共享证据、原生 E2E 与自举验证继续有效。

配对 ABBA 脚本比较本候选与确切的已合并基线。保留全部测量差值，包括冷构建、部分重编译回退与普通小目标对照。确定性的队列和缓存证据证明结构约定，墙钟数据证明该结构是否改善具体负载。单独进行 v5.5.0 发布收尾之前，`VERSION` 保持 `5.4.0`。
