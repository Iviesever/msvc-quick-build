## 017 执行器契约：需要实现和核验的具体路线

下述是实现要求，不是已经实现的正式执行器或调用登记。

1. **先封闭加载输入。** 在被批准的同一宿主内固定 Python、decoder、loader、
   传递依赖、别名/absence、搜索目录及环境；拒绝静态歧义。不得假设候选目录策略
   就是真实 loader 的行为，不复用 016 的旧路径或失配摘要。
2. **区分两种加载证明。** loader 的依赖列表只能作为初始依赖解析证据；不能证明
   Python 后续扩展、stdlib 或 decoder 条件加载。后者需要明确的模块闭集和导入
   策略，冻结源码/模块字节，并对完整合成执行路径检查实际加载行为。仅 `-I/-S`
   或一张 DT_NEEDED 图不足以完成这些证明。若需要运行 loader 或合成 decoder，
   应先独立登记其精确程序/argv、有限输入、输出上限、时限和失败终止方式；本轮不执行。
3. **正式 owner 不收任意范围。** 绑定原五份元数据身份、原 CALL 关联、runtime302、
   原图像以及 `.pdata`/unwind；只给 decoder 经过两份准备核对的 103 B 派生输入。
   输出是连续解码及静态引用，不追踪任意外部目标，不宣称执行过这些机器指令。
4. **资源先于准入。** 把主准备、独立准备、正式观察分开计数；目标输入固定 103 B，
   指令数最多 103，单条指令最多 15 B。图像/元数据总读量、模块总量、stdout/stderr、
   JSON/行长、CPU/地址空间/墙钟和外层保存预算须在完整执行器上审核后冻结，不能
   直接照抄旧 016 的内存或加载证明。超时、输出超限、保存失败均消耗已开始槽位，
   无自动重试、替代 argv/工具、部分成功或隐式下一次分配。
5. **失败保留及批准顺序。** 完成修订源码的独立复核，再实现/审阅上述执行器和加载
   核验，登记精确身份/完整契约之后，才分别分配准备与唯一正式观察。源码合并、
   测试变绿、库存记录或本文件均不授予这些槽位。

目前目标仍为 RVA `[0x1117C,0x111E3)`，103 B；目标 SHA256 为 null。
本轮原图像/新目标内容读取、主准备、独立准备、正式观察和 native 均为 0。
