# 架构决策记录 (ADR) - v4.3.0: MSBuild 1:1 像素级复现与终极并发安全收敛

## Context (背景与缺陷)
基于多域专家（编译器前端工程师、构建系统架构师）对 v4.2.0 及初版 v4.3.0 设计的深度物理验证与交叉对抗，我们发现了数个在工业级落地时足以引发灾难的极限边界条件（Edge Cases）：

1. **同名文件跨目录并发覆盖 (Fatal)**：当多目录并发编译（如 `A\utils.cpp` 与 `B\utils.cpp`）且 `/sourceDependencies` 指向同一输出目录时，MSVC 的默认行为会因输出同名 `.json` 引发多线程竞态锁与数据覆盖。
2. **工具链 ABI 破坏的哈希盲区 (Fatal)**：仅对 CLI 参数进行哈希，无法感知 Visual Studio 工具链升级（如 `cl.exe` 19.38 升至 19.40）导致的编译器二进制接口破坏，旧缓存会引发诡异的链接错误。
3. **PowerShell 路径正规化盲区 (High)**：MSVC 输出的 JSON 偶发包含 `..\` 等未解析宏路径。配合区分大小写的 `.NET HashSet` 时，不经预处理会导致永不命中。
4. **C++20 模块扫描的进程风暴 (High)**：由于 Windows NT 创建进程存在约 30ms 开销，若使用 `foreach` 对上千源文件单次调用 `cl.exe /scanDependencies` 将带来 30 秒以上的性能塌陷。
5. **静态链接器参数白名单 (Medium)**：`lib.exe` 缺乏参数白名单约束，易被 `kernel32.lib` 或 `/LIBPATH` 污染。

## Proposed Solutions (最终防线与架构定版)

在修订版 v4.3.0 中，我们确立了向工业级构建内核收敛的 5 条铁律：

1. **基于目录哈希的分批并发模型 (Collision-Free Concurrency)**
   - 摒弃无脑的全局 `/MP`。对项目源文件按**父目录路径**进行 `GroupBy`，分批次执行 `cl.exe /MP`。
   - 每批的 `/sourceDependencies` 指向独立的临时目录（例如 `.cache\deps\<目录哈希>\`），从物理层面断绝同名文件输出碰撞的可能。
2. **编译器时间戳免疫指纹 (ABI-Aware Hash)**
   - 在计算 MD5 编译参数指纹前，不仅要通过“噪音过滤掩码”滤除 `/nologo`, `/MP`, `/showIncludes` 等控制台输出参数，更必须将 `$ctx.VcDir\cl.exe` 的 `LastWriteTimeUtc` 压入哈希载荷。任何底层工具链的更新都将自动击穿全项目缓存，保障 ABI 安全。
3. **安全正规化的高性能依赖缓存树**
   - 依赖池必须声明为 `[System.Collections.Generic.HashSet[string]]::new([System.StringComparer]::OrdinalIgnoreCase)`。
   - 所有提取出的路径，必须先经过一次 `[System.IO.Path]::GetFullPath()` 剔除 `..\` 和 `.\` 后，再存入或比对 HashSet，消灭一切系统文件系统抽象差异。
4. **宏观批处理预扫描机制 (Macro-Batch Scanning)**
   - 设立二段式模块防火墙。第一阶段通过判断 CLI 是否含有 `-std:c++20/23/latest` 决定是否扫描。
   - 第二阶段扫描触发时，强制将所有待编译文件拼接到**一条**含 `/MP` 的 `cl.exe /scanDependencies` 命令中，由 MSVC 内部多线程解决 IO，将 30 秒的进程创建耗时压缩至 1 秒以内。
5. **隔离独裁的 LinkerBuilder**
   - 对于 `TargetType == "static"`，建立极其严格的白名单：仅放行 `[ "/NOLOGO", "/OUT:", "/LTCG", "/DEF:", "/MACHINE:" ]`，暴力剔除所有 `.lib` 和 `/LIBPATH:` 引用。
