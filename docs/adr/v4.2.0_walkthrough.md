# 架构决策记录 (ADR) - v4.2.0: 构建系统深度缺陷审计与重构提议

## Context (背景与缺陷)
基于多域专家（构建系统工程师、C++ 编译器工程师）的交叉验证，现有的 `build.ps1` (v4.1.0) 启发式引擎暴露出了致命的架构局限。特别是在对比 Visual Studio (MSBuild) 的底层工作流后，我们确认了以下核心死锁：

1. **增量缓存的“冰山盲区”（头文件修改失效）**
   - **症状**：当前 `build.ps1` 仅比对了 `.cpp` 与 `.obj` 的时间戳。若仅修改了 `config.h`，包含它的 `.cpp` 不会触发重编。
   - **根因**：违背了 MSBuild 基于 `TrackerLog (.tlog)` 的真实依赖追踪原则。未将 `.cpp` 的完整头文件树（Header Dependency Tree）纳入增量失效的哈希计算。

2. **BFS 扫描的物理隔离与拓扑断层**
   - **症状**：引擎将 BFS 根节点硬编码为主文件所在目录，导致跨目录（`../Common/`）或非对称 C 库（如 `zlib.h` 对应数十个 `.c`）的源文件被彻底丢弃。

3. **依赖树与外部挂载的生命周期死锁**
   - **症状**：通过 CLI 挂载外部文件时，若主源文件未改，增量引擎短路跳过整个 `cl.exe` 进程，导致挂载文件失去编译载体，触发 LNK1181。

4. **单进程链接强制收敛（缺乏静态库编排）**
   - **症状**：强制写死 `/OUT:.exe`，缺乏目标多态（Target Type Polymorphism）抽象。

## Proposed Solutions (方案对比与演进)

### 方案 C：彻底的 MSBuild 1:1 平替路线 (已否决)
完全废除 BFS 爬取，严格实行显式声明（Track 2）与极简 F5 隔离（Track 1）。
**裁决**：逻辑满分，但产品契合度零分。Track 1 完全剥夺了当前 README 承诺的“基于 #include 自动爬取并编译”这一核心 UX 卖点，带来巨大的断崖式体验落差。

### 方案 D+：融合架构与副产物依赖追踪 (最终定稿)
在充分吸收外部构建专家的二次纠偏后，我们修正了原始方案 D 中“过度预扫描”的性能灾难与“长效缓存暗星效应”，确立了最终执行架构：

1. **输入阶段：双轨制上下文捕获 (Dual-Track Context)**
   - **Track 1 (零配置模式)**：保留 BFS 作为“工作区源文件扫描器”，提取初步的源文件集合，维持“F5 魔法”。明确声明其对“非对称 C 库”的局限性，靠 LNK2019 抛出降级提示。
   - **Track 2 (项目模式)**：读取 `msvc_list.json` 中的 `sources`（支持 Glob），**全面接管/覆盖 BFS**。支持 `target_type` (exe/static)。

2. **图构建阶段：解耦拓扑扫描与头文件依赖**
   - **拓扑预扫描 (Pre-scan)**：仅对 `.ixx` 或正则匹配包含 `import` 的文件执行 `/scanDependencies`，以建立 C++20 模块的 Kahn 排序。杜绝对纯 C/C++ 源文件进行无意义的预扫描。
   - **副产物依赖追踪 (By-product Tracking)**：在后续真正执行 `cl.exe /c` 编译源文件时，**顺手附带 `/sourceDependencies <file.json>` 参数**。编译器会在输出 `.obj` 的同时，以零额外时间成本生成完美的头文件依赖树。

3. **编译阶段：Tlog 级的高精度增量失效传播**
   - **缓存命中规则**：一个 `.obj` 必须重编，当且仅当：
     1. 其自身 `.cpp` 修改时间 > `.obj`。
     2. 或其关联的 `.json` (由上一次编译顺手生成) 中记录的 **任意** 头文件/导入模块的时间 > `.obj`。
     3. 或编译参数（Flags）发生变化。
   - 完美解决头文件修改不编译的 Bug，同时消除了由“长效缓存未随头文件图谱演变”引发的连通性死锁（暗星效应）。

4. **链接阶段：管道多态化**
   - 引入 `LinkerBuilder` 抽象，根据配置路由至 `link.exe` 或 `lib.exe`。

## Implementation Edge Cases (最后 1% 的底层逻辑补丁)
为确保架构 100% 落地不留暗坑，编码时必须严格遵守以下约束：

1. **“幽灵依赖”拦截 (Ghost Dependencies - 对齐 Ninja Phony Targets)**
   - **约束**：在解析上一次的 `.dep.json` 判定缓存时，必须检查每一个文件是否存在 (`Test-Path`)。若任意历史依赖文件物理丢失，**必须无条件击穿缓存触发重编**，将 `C1083 Cannot open include file` 的正统错误抛给真正的 `cl.exe` 处理，严防脚本层默默崩塌或误判命中。
2. **`/sourceDependencies` 并发写冲突防范**
   - **约束**：在多进程（`/MP`）编译参数中，绝不能只指定 JSON 目录，必须为每个编译单元 (TU) 显式映射物理隔离的绝对路径（如 `/sourceDependencies "...\main.cpp.dep.json"`）。
3. **优雅的异常降级路由 (LNK2019 UX)**
   - **约束**：建立链接器双路重定向捕获（兼顾控制台输出与变量捕获）。在检测到 `LNK2019:.*unresolved external symbol` 特征时，高亮打印明确引导，建议用户使用 `msvc_list.json` 的 sources 字段应对复杂非对称 C 库。

## Impact Matrix (破坏性与回归测试风险评估)

| 模块 | 影响范围 | 风险评估 | 缓解策略 |
|---|---|---|---|
| BFS 引擎 | 低 | 降维为纯文件提取器。 | 增加 LNK2019 异常捕获机制进行用户心智引导。 |
| 增量与编译引擎 | 极高 | 彻底重写基于 `.json` 的 DAG 缓存模型。 | 严格落实“幽灵依赖”断言。针对分支切换导致文件丢失的场景进行破坏性测试。 |
| 编译参数 | 中 | 需要全面注入 `/sourceDependencies`。 | 极速兼容 C++20 编译管线，并在 CLI 组装时落实防并发冲突补丁。 |
