# 模块 target 的同次缓存证据

[English](MODULE_TARGET_CACHE_EVIDENCE.md) · [下层编译波契约](MODULE_CACHE_EVIDENCE_ZH.md)

## 契约

`MsvcModuleTargetCoordinator::run_recorded` 在既有 `result`、`record` 旁附带拥有型
`ModuleCompileWaveCacheEvidence cache_evidence`。编译阶段只调用一次既有下层记录接口，
直接将返回值移动到私有可选暂存；原完整 target 成功且所有阶段值存在后才对外返回。
不能用默认空值冒充已经丢失的证据。

`compiles` 对应实际准备后的 source 顺序：先是请求源，再是实际选择注入的
`std`／`std.compat` 提供者。`header_unit_compiles` 对应动态准备后的 HU 顺序，
与原编译波结果和投影一一对应。HU 不伪造扫描，外部提供者仍是引用，不虚构本地产物缓存值。

## 保持的行为

不为补证据而额外读取缓存、扫描、构造签名、编译或链接。默认 `run` 仍传空记录指针，
`inspect`、CLI、路由、普通及静态 target 不改变采用方式。原扫描、图、编译、链接错误直接
传播；失败不发布部分成功缓存记录，也不承诺回滚此前已经写入的文件。

旧阶段结果、调用者标签、投影及类型化缓存保存警告保留。新增拥有值不提高旧投影的精确捕获
标志，也不授予生产者身份、当前内容、完整产物清单或删除权限；它不是持久化生产者证明、
历史存档、写者租约或安全清理许可。

## 验证

沿用十次 mock 和十次 native target 调用，保留全部原断言与工具预算。冷／热、共享输出、
修复、配置覆盖及实际注入提供者的成功用例，核对各 source／HU 值、对应投影和同次缓存字节。
热调用严格核对整个 target 的计数：每份扫描记录（请求源及实际注入提供者）一次成功载荷打开，
再加每个编译波节点（source／HU）一次打开，且零写入。因此一个热 source 在两个阶段共读取
两次，HU 只读取一次；外部提供者引用不增加节点预算。一般调用最多允许这些扫描与节点打开，
每节点最多一次保存尝试；失败的文件打开不计成功读取。原始计数和范围先落盘，再执行断言，
计数不包含测试序列化。纯编译期正反控制拒绝额外读写、缺失的热读取及虚构的 HU 扫描。
阶段错误仍不产生成功证据文件。在后续覆盖及失败之后重新序列化先前冷热和标准库缓存值，
检查返回值自身的所有权与历史保全。

便携测试仅逆转准确的附加扩展，再验证原程序整体 blob，不删除旧检查。新增反例拒绝复制值、
默认值、缺值、重复调用、额外 I/O、改写失败守卫或默认采用。这些源码／序列化检查不等于
真实 MSVC 执行，仍需该候选自己的 Windows 原始证据。

## 成本与发布边界

传递过程移动已经生成的向量，不复制或重读；但原本会被上层丢弃的载荷现在保留到成功返回值
被调用者释放，失败时保留到本次调用展开结束。因此峰值与驻留内存可能增加。既有显式路径
请求／工具链复制和分配成本仍未量化，不承诺零成本、无性能回退或可默认高频采用。

这只是 #198 的一个实现步骤，不是 v5.7.0 发布或完整 Rium 资格。原不利性能证据、已消耗实验、
持久化／写者／清理限制继续保留；候选功能验收与独立性能／集成决定仍需分别完成。
