## Joining invocation references to an observation (internal, opt-in)

`project_storage_references(record)` produces an owned, deliberately limited path projection from the existing ordinary/static target, LINK/LIB, PCH, module scan/compile/wave or complete module-target record. Each stage retains its kind, executed/reused state, available configuration/cache state and source warning flag. Input, declared-output and metadata-reference roles remain separate. The PCH creator is both a compiler input and materialized-state declaration; reuse never means it was just rewritten. Scan metadata does not imply a saved compilation cache, P1689 declarations do not become physical outputs, and header units never gain a guessed object. Old ordinary source records lack their own working directory and exact save state; the projection does not borrow those from the final linker. Configuration is not full recipe identity. Raw arguments, inherited environment values and unrelated P1689 fields are not serialized or interpreted by this projection.

`associate_artifact_storage(projections, observation, path_key)` is a pure join over these values and an already collected `StorageInventory`. The composition caller supplies the existing Windows `path_identity_key`, not a filesystem-probing canonicalizer. No scanning, cache reading, building, hashing of file content, deletion or mutation of the original inventory occurs. The result owns both inputs so its indices survive later changes to the caller's vectors. Caller labels are not unique identities: matches retain record/stage/path indices, and repeated references across records or stages are not collapsed.

Absolute references use their own spelling; relative paths require their own stage's recorded absolute working directory. Empty paths, NUL and parent traversal remain unresolved rather than borrowing the inventory root or process cwd. Rooted relative Windows paths are not guessed. Invalid inventory roots/rows and empty path keys reject the join; callback exceptions propagate without a partial successful return. Rows, projected paths and expanded direct/alias links each have a 1,000,000 limit; excess rejects the whole join rather than silently truncating coverage. No symlink or junction resolution is performed. `not_observed` means absent from this supplied row list, not proven absent on disk; original partial-scan issues and unavailable/reparse rows stay visible. `ambiguous_path` preserves every row for a colliding path key instead of selecting one.

A unique regular-file path match may expose other rows with the same **observed** physical ID. These alias rows are separate from direct path matches; incompatible available sizes/link counts are flagged, not resolved. Missing metadata does not certify consistency, and observing two names is not proof all hard links were found. Neither this ID nor a successful path join binds today's bytes to the earlier invocation. Same-path replacement/configuration overwrite remains possible. Unmentioned rows are not obsolete; matched inputs are not owned outputs. There is no summed reclaimable-byte result, retention rule or delete plan. Invocation-identity, current-content and deletion proof flags remain false. This API does not change `mqb storage` JSON or enable default CLI recording.

The independent association E2E retains the original86 test sources (87 total). Portable cases exercise shared and duplicate references, colliding labels, configuration/reuse preservation, unknown cwd, invalid paths, conflicting alias observations, partial scans and owned snapshots. Windows runs four ordinary recorded targets (cold, reuse, shared, Release), seven bounded observations, one successful program and one fixture junction command. Real hard-link, removed-path, same-path replacement, busy-file and reparse observations are retained before assertions under `storage-evidence/association`; toolchain discovery is separate. The fixture modifies only its own fresh test tree and runs the successful program before intentional file changes. It does not measure concurrent writers, recorded-API overhead or Rium behaviour. The original native suites, self-host/package and19×4 ABBA gates and every prior specialised-performance limitation remain in force.
