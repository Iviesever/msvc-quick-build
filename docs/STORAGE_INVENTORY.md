# Read-only storage inventory

**English | [简体中文](STORAGE_INVENTORY_ZH.md)**

This is the first development slice of #198, based on v5.6.0. It is not part of the published v5.6.0 executable and does not complete v5.7.0. VERSION remains 5.6.0 until an independent release PR.

## Commands and scope

```powershell
mqb storage
mqb storage --project C:\work\Rium --format json > C:\reports\rium-storage.json
mqb storage --help
```

The default project is exactly the current directory; the command does not search for mqb.json, load configuration, discover a toolchain, build, run a product, or create .mqb. It reuses ProjectArtifactLayout for the requested existing project directory. A missing .mqb produces an empty observation. Unknown/duplicate arguments are usage errors. No clean, prune, execution switch, age filter, or retention policy is implemented.

Stop builders and other writers first. Output goes only to stdout/stderr; redirect outside .mqb. Read handles temporarily deny write/delete sharing and can therefore cause a competing writer or rename to fail. This is not a build/clean mutual-exclusion protocol, a project lease, or a guarantee against external noncooperating activity.

## Bytes and evidence categories

JSON schema_version 1 supplies per-file raw unsigned logical_bytes, allocated_bytes, hard_links and physical_id; unavailable fields are null, never guessed zero. Decimal GB is 1,000,000,000 bytes, GiB is 1,073,741,824 bytes. Text reports include the same raw file list and summaries.

Directory groups contain direct children only. Extension, direct-directory and evidence groups are disjoint partitions of observed regular-file rows; their known logical totals close against totals. Path allocation repeats each hard-link pathname deliberately. unique_file_allocated_bytes deduplicates observed volume/file IDs; conflicting sizes or any observation issue make it unavailable. Allocation is not reclaimable capacity: links outside the root, filesystem deduplication, metadata and unobserved activity are not established by this count. Compressed/sparse physical allocation is explicitly unavailable in this slice. Alternate data streams and directory metadata are excluded.

Evidence is protected, unknown, cache_reference, or shared_cache_reference. Extensions are descriptive, not authority. Logs, generated inputs, release packages, VS state, unknown directories and non-files remain protected. The ordinary bin/obj/ifc/deps/scan/cache/pch locations are not thereby authorized for deletion: their lifecycle remains unknown. reclaimable_bytes, live_bytes and obsolete_bytes are always null; deletion_authorized is always false.

## Historical references are not ownership

The existing LinkCacheFile and ArchiveCacheFile readers are reused only for observed cache/link/*.linkcache and cache/archive/*.archivecache files of at most 16 MiB. They are never saved or upgraded. Corruption, unsupported data, oversize data and decoding errors remain visible. Only absolute references are compared with observed paths using MQB's established Windows path identity. Referenced external paths are not opened; relative legacy paths have no established base and are not guessed.

Each record reports its cache path, output, opaque signature and tool version. More than one record referencing a row means shared historical references, not proven current shared ownership. Per-target totals overlap and must not be added together. The old signature cannot reveal Debug/Release or a complete target configuration; by_configuration is therefore unknown. Neither a missing source, an old hash nor omission from the current invocation proves retirement. Tracking trustworthy current targets, shared dependencies and explicit AOT generations remains a separate prerequisite for future deletion.

## Filesystem and error boundary

Windows metadata reads use handle-based FileStandardInfo and FileIdInfo. Each opened file and its ancestors stay pinned during its observation; reparse points are refused rather than traversed. Pins request FILE_READ_DATA (FILE_LIST_DIRECTORY for directories) together with FILE_READ_ATTRIBUTES, not attribute-only access, so the read-only sharing mask participates in Windows sharing checks. Permission to read data/list directories is therefore required even when only metadata is reported. An access failure remains a partial observation; there is no attribute-only fallback. Enumeration is bounded to 1,000,000 rows and depth 128. The read is not an atomic filesystem snapshot: atomic_snapshot is always false, including a successful walk. Permissions, sharing failures, unsupported identity/allocation, skipped reparse subtrees and enumeration/decoder errors produce issues and exit 1 with a partial report where rendering remains possible. Fatal setup/render failures may yield diagnostics without a complete JSON document. Consumers must check exit status, parse success, complete and issues.

Exit 0 means the bounded walk completed without recorded issues, not that the tree is immutable or cleanup is safe. Exit 1 means observation/output failure or partial coverage. Exit 2 means invalid arguments/project setup. No file is removed, no process/service is killed, and no compiler flags or ordinary build/cache behavior change.

Primary contracts: [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info), [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex), [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew). These APIs alone do not establish reclamation or concurrent-writer safety.

## Reproduction and acceptance

The new mqb_storage_e2e_tests.cpp retains all original 79 native programs and becomes the 80th. Portable model/report contracts exercise byte closure, reference deduplication, protected entries, unavailable/overflow values, JSON escaping and output failures; they do not test Windows.

The Windows fixture covers an absent root, valid/shared/corrupt legacy records, real hard links, Unicode/space paths, existing writers, attempted file/ancestor renames and write/delete access during observation, successful access/rename controls after handles close, unchanged file names/contents/mtime and a real junction refusal. Each pinning result and native error code is saved before its assertion, including on failure. Each Debug/Release native test execution has exactly eight two-TU builds: stable cold/repeat, source rename, target rename, configuration switch, two AOT-named targets and last-target repeat. It runs the last produced program once, preserves old objects/targets and checks inventory byte/file closure without deleting them. These AOT names are a minimal lifecycle model, not a run of Rium's AOT generator.

Raw argv/stdout/stderr/exit and original successful/failed inventories are retained in storage-evidence, with selected sources, target outputs and link-cache files in CI artifacts for 30 days. Existing native Debug/Release, self-host/package, applicable compatibility workflows and independent 19-by-4 ABBA remain acceptance gates; a portable pass is not their substitute. No fixed space-saving percentage is promised. Actual Rium validation, trustworthy ownership/configuration state, compressed/sparse accounting and safe clean/prune remain pending.

## Successful invocation records (internal, opt-in)

The next producer-side slice adds `MsvcIncrementalTargetCoordinator::run_recorded` for ordinary EXE/DLL targets and `MsvcIncrementalLinkCoordinator::run_recorded` for terminal links. They execute the same validated pipeline once and return an owned result plus typed associations only on success. This is an internal C++ API, not a new CLI command, persistent registry, target transaction or change to `storage` JSON.

Target records keep source/object/dependency-metadata/cache references in source order, both compiler and effective link options (including their separate configurations), and optional caller-supplied target/generation annotations. An absent annotation stays absent; changing a label never invalidates caches or turns reuse into a produced generation. Shared source objects appear in each relevant target record. Additional/PCH-style objects stay input references, not outputs owned by the ordinary scheduler. Metadata/cache paths are references, not proof those files were saved; compile warnings and the complete original result remain available.

The link record reuses the exact in-memory LinkCacheEntry sealed after successful linking, or the entry accepted by this invocation's existing cache validation. It does not rebuild recipes, reread the cache, add filesystem probes or write a journal. Executed and reused are separate outcomes. Cache-save failure remains a warning with `save_failed` state, never a durable-record claim; link failure or a missing required MAP output returns the original error and no successful record. Conditional side outputs are those already tracked by the linker authority, not files guessed from extensions. This is not a complete list of LINK's possible effects or its actual argv.

These are **successful invocation associations, not physical output observations or lifecycle authority**. No file-ID/content hash, concurrent-writer exclusion, current-content check, crash recovery, disk serialization or retention rule is added. Existing caches remain byte-format compatible. Past success survives only as caller-owned data; later configuration overwrite or failed work can invalidate the actual files. Old files and `storage` liveness/reclaimable fields remain unknown. Static-target and PCH support are described below; module integration, persistence and readback require separate work before cleanup can be considered. No default CLI caller opts in.

The existing 80 programs remain, plus the new artifact-record E2E program (81 total). Portable value-model tests check optional labels and upstream-input separation; eight deterministic link-coordinator calls cover executed/reused, same-path configuration changes, original link failures, corrupt caches, cache-save failure, conditional DLL outputs, and missing MAP. The new artifact-record E2E program performs exactly seven real recorded API calls per native configuration: cold, reuse, shared target, Release overwrite, source rename, expected compile failure, and a separate DLL target. It discovers one toolchain and runs one produced program, retaining process argv/output/status and completion summaries under `storage-evidence/records`. This is additional to the original eight CLI builds/five storage calls, uses a fresh fixture, and never retries the failed EXE build. No actual Rium AOT validation is implied.

## Static-library successful-call records (internal, opt-in)

`MsvcIncrementalStaticTargetCoordinator::run_recorded` and `MsvcIncrementalArchiveCoordinator::run_recorded` extend the same producer boundary to ordinary static targets and terminal LIB. The archive record uses the exact ArchiveCacheEntry accepted by this invocation's validator or sealed after the librarian successfully installs its output. It reports the final `.lib` path, not the `.mqb-tmp` path. Original tool/installation/parameter failures return no successful record. A cache-save warning remains `save_failed`, not a durable-success claim.

Architecture, effective LTCG and passthrough arguments come directly from the existing librarian parameter authority; a raw `/LTCG` must be represented correctly on both executed and reused calls. No second parameter parser, extra filesystem scan or cache reread is added. Static records reuse the existing source-association and caller-label types, separately retaining compiler configuration and upstream object inputs. Only explicit recorded calls assemble source records. Default CLI paths do not opt in; the shared default implementation changes, so zero overhead is not promised and independent performance gates remain required.

**Archive recipe identity is not compile configuration or content identity.** Debug/Release can overwrite the same objects and library with the same archive recipe signature. The compiler options and original compile results must be read separately. Caller generation labels do not create unique generations, and a cache hit never becomes a new produced archive. PCH creator support is described below; module producers, physical file identity, concurrent-writer boundaries, persistence/readback and Rium validation remain pending. No cleanup, transaction/lease, retention policy or storage JSON change is introduced.

The original 81 programs are retained byte-for-byte. The new static-record E2E program makes 82 and allocates, per native configuration, ten deterministic archive calls with mock processes and real cache/file I/O: cold/reuse, routed LTCG/reuse, cache-save failure, corrupt cache, parameter conflict, original nonzero LIB exit, missing temporary output and failed output installation. Six real static-record API calls cover cold/reuse, a second target using a shared/upstream object, same-path Release overwrite, source rename and expected compile failure. One independent ordinary EXE consumer build/run verifies the last successful library without retrying the failed static build. The fixture uses one toolchain discovery and a single worker.

Original argv/stdout/stderr/status, each mock/native result and per-success native library/cache copies are retained under `storage-evidence/static-records`, outside `.mqb`, with mock and real evidence separated. These are test-only copies, not product persistence, all-producer snapshots or concurrency proof. No retries replace failures. The old storage and EXE/DLL record tests, full native Debug/Release, self-host/package/installer and unchanged independent 19-by-4 ABBA remain separate acceptance gates.

## PCH creator successful-call records (internal, opt-in)

`MsvcIncrementalPchCoordinator::run_recorded` returns the original successful PCH result plus an owned `PchArtifactRecord`. The record uses the same invocation's existing creator-request projection: input header, synthetic creator TU, paired object/PCH output declarations, actual create binding and compiler options, dependency/cache references, working directory and optional caller annotation. It never copies an unmodified caller use binding and calls it a creator. The input header is not an output, and the generated creator source is distinct from its compiled outputs.

Executed/reused comes from the actual compile result, including the existing second freshness check after materialization. Saved/save_failed comes from the original typed compile-cache-save warning, not text parsing or a fresh cache read; reused is not a new cache save. Original diagnostics and errors remain. The warm path stays read-only; the same-timestamp creator repair and its internal force/recheck mechanism are unchanged. `creator_source_materialization_required` describes the initial same-call inspection, not proof of an exclusive or atomic write. Failed materialization, compilation or missing PCH never returns a successful record. An old record does not guarantee later failed work left its files intact.

**This record is not an exported CompileCacheEntry.** The lower compile API does not expose that entry; this slice does not change the lower coordinator, reread a cache, reconstruct a signature or invent include/module metadata. `exact_cache_entry_captured`, `physical_identity_verified`, `complete_producer_inventory` and `deletion_authorized` are false. It is a creator association, not a complete PDB/other-side-effect inventory, byte identity, durable lifecycle or deletion authority. Default CLI does not opt in; shared wrapper costs remain subject to validation. Storage JSON, cache formats, persistence and concurrency behavior are unchanged.

The original 82 native programs remain byte-identical. One PCH-record program makes 83. Per native configuration it allocates ten deterministic PCH calls (mock cl, real coordinator/cache I/O): cold/reuse, same-mtime creator repair, missing-PCH repair, cache-save failure, compiler failure, missing PCH after tool success, blocked creator source, missing header and invalid output. Full completion has five successes, five expected errors and six mock processes. Six real PCH-record calls cover cold/reuse, same-mtime repair, same-path Release overwrite, header change and expected compile failure. One ordinary EXE consumer build/run uses the last successful PCH and paired object **before** the deliberate failure; failed work is not retried. One toolchain is discovered; the consumer uses one worker.

Raw commands, statuses, warnings and each successful native creator/object/PCH/dependency/cache copy are retained under `storage-evidence/pch-records`, separated into mock/native groups. These are test copies outside `.mqb`, not product persistence or complete filesystem snapshots. The old storage/EXE/static tests and all existing native, self-host/package/installer and independent 19-by-4 ABBA gates remain. Standard ABBA still lacks a dedicated static/LIB scenario; its previously accepted coverage gap and all unfavorable historical samples remain unresolved. Broader recording and final v5.7/Rium qualification need the separately registered static study. Module producer coverage, actual file identity and durable readback remain separate prerequisites for cleanup.

## Module compile-wave successful-call records (internal, opt-in)

`MsvcModuleCompileCoordinator::run_recorded` executes the existing compile wave once and returns its original result with an owned `ModuleCompileWaveArtifactRecord` only when the whole wave succeeds. Its provider selection is the caller's typed `ModuleDependencyPlan`, accepted by the existing plan checks; per-node `ModuleCompileArtifactRecord` values are taken from the actual compile requests and successful returns in that same invocation. No extra inspection, scan, compilation, provider-name guess or cache read is introduced. Source records and header-unit records each preserve their request order, independent of graph levels and worker completion. Recording slots are allocated before scheduling and each worker writes only its own slot; the default path does not allocate record vectors.

The node records retain the projected translation unit, actual compile options, cache/dependency paths, optional prior scan reference, working directory and propagated `force_rebuild`. Module/header IFC inputs are references, distinct from outputs. Named interfaces declare object plus IFC, ordinary consumers an object, and header units only IFC according to the existing request factory. External providers remain graph/IFC references and are never synthesized as new owned producers. The graph does not contain a complete set of P1689 provider declarations; unreferenced logical names are not invented. A prior scan path is not an output produced by this compile call or proof the scan is current.

Executed/reused and saved/reused/save_failed reflect the real returned compile result and typed cache-save warning. The original result retains all warnings and diagnostics. Failure returns the original wave error, without a partial public success record; earlier successful nodes can already have written outputs or caches. This is not rollback, an atomic snapshot or a current-state certificate. The lower compile API is unchanged and still does not export its accepted/sealed cache entry; exact_cache_entry_captured, physical_identity_verified, complete_producer_inventory and deletion_authorized remain false. Caller labels are annotations, not unique generations. Default CLI/module-target callers do not opt in; no persistence, physical identity, side-effect inventory, retention or cleanup authority is added.

All original 83 test sources remain byte-identical; one new module-record program makes 84. Per native configuration it has ten mock-process waves (five successes/five expected errors): cold/reuse, missing-IFC repair, cache-save warning, provider failure, tool success without IFC, artifact collision, unresolved requirement, invalid provider and header-only wave. It uses the actual typed graph builder with separately labelled synthetic P1689 values, including an external IFC, and at most sixteen mock compile processes. The native fixture performs three initial real P1689 scans for two named modules and a consumer importing a header unit, then six recorded waves (five successes/one expected compiler failure): cold/reuse, IFC repair, same-path Release overwrite, provider body change and provider failure. Later mutations keep import/provider topology unchanged; this tests the explicit compile-wave layer, not whole-target rescan freshness. Six waves have an upper bound of twenty-four compiler calls, with unused budget left unused. One final link of the three actual source objects and one program run returning 13 occur before deliberate failure; no header-unit object is fabricated. Toolchain discovery is separate.

Before-call inputs/specifications, actual process argv/stdout/stderr/status, original errors/warnings and successful node input/output/dependency/cache copies are retained under `storage-evidence/module-records`, with mock/native separated. Copies are test evidence, not product persistence or complete snapshots. Original storage/EXE/static/PCH tests and independent native Debug/Release, self-host/package/installer and 19-by-4 ABBA gates remain. Standard module timings do not measure this explicit recording API; dedicated PCH/static and opted-in recording costs remain unmeasured. Preserve historical adverse samples and require separately registered representative comparisons before broader integration/final v5.7 or Rium qualification. Scan-producer records, full target completion, actual file identity, persistence and concurrency/readback remain later work before cleanup.
